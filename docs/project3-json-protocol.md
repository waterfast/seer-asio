## 目标（一句话）

把"一行文本命令"换成"一条 JSON 消息"，让消息能表达**结构化数据**——尤其是能带空格、带多个字段。

## 为什么现在做这个

项目 2 你已经撞到文本协议的天花板了：

- `SAY` 只能一个词（参数含空格就 402）
- 参数只能是一串扁平的词，表达不了"用技能 + 目标 + 威力"这种结构
- 每加一种消息都要重新发明一套文本格式

JSON 就是来解这个的。它不是"更高级的玩具"，是你项目 2 那套东西**换了个更宽的壳**。

---

## 这一课真正的三个考点（是想清楚三件事，不是三个任务）

### 1. 分帧：JSON 里可以有换行，那"一条消息"怎么切？

现在 `ClientSocket::reader()` 按 `'\n'` 切。JSON 文本里可能出现换行，按行切就不够用了。两条路，你选（或都试试）：

- **NDJSON**：每条 JSON 压成一行（不允许裸换行），继续按 `'\n'` 切。最简单，先跑通。
- **长度前缀**：4 字节长度 + 消息体，收方先读长度、再读满 body。这是 freekill 的做法
  （它 `Packet` 里的 `_len` 字段），也更通用——以后换二进制还得靠它。

提示：**不必一次到位**。可以先用 NDJSON 把"JSON 能跑通"这件事做完，再升级成长度前缀。

### 2. 消息长什么样？

这是你的自由发挥区。给两个参考方向：

- 类型字段 + 展开字段：`{"type":"UseSkill","skillId":1001,"targetId":3}`
- freekill 式 command + data 分离：`{"command":"UseSkill","data":{...}}`

关键是你得回答一个问题：**分发的依据是什么**？项目 2 是"第一个 token"，现在应该是 JSON 里的某个字段。

### 3. 谁负责解析 JSON？放在哪一层？

值得想的设计题：

- 网络层只交"原始字符串/字节"，业务层解析 JSON（网络层更干净，但多处要各自解析）
- 网络层解析成消息对象再回调（freekill 的 `ClientSocket` 就这么干：它在 `handleBuffer`
  里把 CBOR 解成 `Packet` 才回调）

两条都行，但**想清楚再动手，别让解析逻辑散落两处**。

## 必须守住的底线（这些不是可选项）

- **坏输入不能崩**：非法 JSON、缺字段、类型不对 → 回一条结构化错误消息，协程不能异常退出。
  这是"服务端是权威"的第一课。
- **响应和请求能对上**：客户端连续发多条时，回包得知道对应哪条。想想要不要 `requestId`
  （freekill 的 `Packet` 里有）。
- **错误也要结构化**：`{"type":"Error","code":400,"message":"..."}` 这类，别退回到文本 `ERR 400`。
- **网络层/业务层的分界别含糊**：解析放哪定了就贯彻到底。

## 客户端怎么办（自己定）

控制台客户端要发 JSON，有个现实问题：让用户手敲原始 JSON 太痛苦。

- 方案 A：客户端保留命令式输入（`use_skill 1001`），客户端负责翻译成 JSON 发出去
  ——你项目 2 的切词代码能直接复用。
- 方案 B：直接要求输入一行 JSON。

你定。只要**服务端只认 JSON**就行。
